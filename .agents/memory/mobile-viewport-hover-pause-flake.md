---
name: Full-page screenshot + mask tiling race on tall pages
description: Root cause (confirmed) of the intermittent Nova Havens mobile-chrome/mobile-chrome-dark "home renders correctly" full-page screenshot flake, and the fix.
---

**Confirmed root cause:** `expect(page).toHaveScreenshot({ fullPage: true, mask: [...] })` on a very tall page (Nova Havens home is ~14857px on a 390×844 mobile viewport, needing ~18 stitched scroll tiles) occasionally produces an intermediate capture where mask boxes land on the wrong tile — e.g. the carousel's `<img>` renders unmasked (real photo visible) while a phantom magenta mask box appears over the unrelated FAQ section further down. This is Playwright's own full-page-tiling + per-locator mask bounding-box computation racing against layout on pages needing many tiles; it is not caused by app code. Every observed failure eventually converges to a capture that is byte-identical to the committed baseline — it's a matter of Playwright's internal "two consecutive stable screenshots" polling needing more time on this page, not a real visual regression.

**Ruled out (do not re-investigate):** hover-to-pause on the homepage's autoplaying showcase carousel (`carousel-showcase`, pauses via `onMouseEnter`/`onMouseLeave`) was the original suspect since only `isMobile: true` projects flaked. Confirmed by direct instrumentation that `locator.hover()` fires real `mouseenter`/`mouseover` events identically under `isMobile: true` + `hasTouch: true` (mobile-chrome) and `isMobile: false` + `hasTouch: true` (tablet-chrome) — hover-based pause works fine on both. Don't re-chase this lead.

**Fix applied:** raise the `timeout` option on that specific `toHaveScreenshot` call well above the 5s default (e.g. 20s) so Playwright's stability polling gets enough tiling attempts to converge. This does not loosen `maxDiffPixelRatio` and does not risk hiding a real regression — a genuine layout change still fails, just after more retries. Verified with 13 consecutive clean runs (8× mobile-chrome + 5× mobile-chrome-dark) after the fix, versus roughly 2/7 failing before it.

**How to apply:** if a `fullPage: true` + `mask` screenshot test flakes specifically on the tallest/narrowest viewport (more tiles) and nowhere else, and the saved "previous"/"actual" diagnostic images from a captured failure show a mask box on an element that shouldn't have one (or missing from one that should), suspect this tiling race before suspecting app-level animation/timing. Compare the failing capture's MD5 against the baseline — if they match, the "instability" is Playwright not converging in time, not a real diff.

**Also seen on tablet-chrome-dark:** the same "home renders correctly" test failed once on `tablet-chrome-dark` (not just the mobile projects) with a reported image-height mismatch (~26px) despite no app-code change touching page layout that run. A fresh isolated re-run of just that test/project passed cleanly, confirming nondeterministic capture instability rather than a real content-height change. Any project rendering this same tall page can apparently hit the tiling race occasionally, not only the two mobile projects — before suspecting a real regression, re-run the single failing test/project in isolation first.
