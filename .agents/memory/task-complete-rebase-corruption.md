---
name: markTaskComplete rebase can corrupt files
description: A rejected markTaskComplete's validation step can silently rebase the branch onto a moving shared upstream ref, and a bad automatic conflict resolution can corrupt a file with no visible conflict markers.
---

**What happens:** calling `markTaskComplete` triggers a validation pass that can rebase the local `main` branch onto `main-repl/main` (a shared ref that other concurrent agents/tasks push to). If `main-repl/main` advanced with unrelated commits touching the same file as your work (e.g. another task refactoring the same test spec file), git's automatic conflict resolution during that rebase can produce a syntactically-broken, textually-spliced file — WITHOUT raising a conflict or any visible error. The task then fails validation (e.g. a test runner reporting "0 tests" from a `ReferenceError` at module scope) for a reason that looks like your own authoring mistake but is actually rebase damage.

**Why:** `main-repl/main` is a shared/moving ref; other tasks can land commits on it between your session's start and your `markTaskComplete` call. Rebasing replays your commits' diffs against the new base via a 3-way merge, which can silently misapply a patch (fuzzy-matched hunks, spliced fragments) when both sides touched nearby/overlapping regions of the same file.

**How to recover:** check `git reflog` for a `rebase (start)/(pick)/(finish)` sequence around the time the file broke — this confirms rebase-induced corruption rather than your own edit. The `gitsafe-backup/main` and `gitsafe-backup/HEAD` refs get updated to your branch tip immediately before such a rebase, so `git show gitsafe-backup/main:<path>` recovers the pre-rebase content. Reconstruct by taking the CURRENT `main-repl/main` version of the file (which has legitimately evolved — do not blindly overwrite it) as the base, then re-apply only your own task's diff on top, rather than restoring the backup wholesale (that would revert other agents' legitimate concurrent changes). Verify structural soundness (e.g. a test runner's `--list`/collect-only mode showing the expected test count) before trusting any subsequent full test run — a run against a still-broken file can look like a pass if you're misreading stale log output captured before the corruption happened.

**How to apply:** whenever a completion-validation failure reports a structural/syntax error in a file you were confident was correct and already verified, suspect this before suspecting your own authorship — check the reflog first, and cross-check file mtimes against your last known-good test run's log mtime.
